# pre-merge:main に入れる前のチェック

このプロジェクトはハッカソン用で、メンバーの多くは初心者です。土台担当は全部の PR を確認できません。
このスキルの目的は、**他の人のコードを意図せず壊していないか** と **プロジェクトのルールから外れていないか** を、PR を出す本人と一緒に確認することです。
セキュリティの診断はしません。

## 進め方の原則

- ユーザーへの説明は日本語で、専門用語には「アプリでどう困るか」を一言添える。
- **チェックの途中で勝手にコードを直さない。** 問題を見つけたら、直し方の案を出し、ユーザーの了承を得てから直す。
- 止めるべき問題(下の「土台担当への連絡が必要」)があったら、PR の本文を書く前にそれを伝える。

## 手順

### 0. 準備

1. ユーザーの担当を確認する。ブランチ名や変更ファイルから推測できなければ、次のどれかを聞く。
   - 引力・描画(`src/features/gravity/`)
   - 写真(`src/features/photo/`)
   - BLE(`src/features/encounter/`)
   - 土台
2. 比較する基準を最新にして、変更の一覧を取る。
   ```bash
   git fetch origin
   git status --porcelain
   git diff --name-status origin/main...HEAD
   ```
   コミットしていない変更も対象に含める。

### 1. 型と Lint(アプリが起動するかの最低限の確認)

```bash
npx tsc --noEmit
npx expo lint
```

エラーがあれば、ここで止めて直し方を提案する。型エラーが残ったまま main に入ると、全員のアプリが起動しなくなる可能性がある。

### 2. 変更したファイルを分類する

変更したファイルを、`git diff --name-status` の記号で次の3つに分ける。

| 記号      | 種類             | 扱い                                                                            |
| --------- | ---------------- | ------------------------------------------------------------------------------- |
| `A`       | 新規追加         | 基本的に OK。ただし、すでに同じ役割のものがないかを検索して確認する(重複を防ぐ) |
| `M`       | 既存の変更       | 自分の担当フォルダの中なら OK。**担当フォルダの外なら手順 3 へ**                |
| `D` / `R` | 削除・名前の変更 | 自分の担当フォルダの中なら OK。**担当フォルダの外なら手順 3 へ**                |

### 3. 担当フォルダの外の既存ファイルを、変更・削除していた場合

ファイルごとに、次を確認してユーザーに示す。

1. **何を変えたか**:差分を短く要約する。
2. **誰が使っているか**:変更・削除した関数・型・コンポーネントの使用箇所を検索する(例:`grep -rn "関数名" app src`)。どの担当のコードが影響を受けるかを書く。
3. **意図した変更か**:ユーザーに「この変更は意図したもので、Claude と相談したうえで決めたものか」を確認する。意図していなければ元に戻す案を出す。
4. **代わりの方法**:既存を変えずに、新しい関数・型を追加すれば済まないかを検討して示す。済むなら、そちらを勧める。

特に注意する変更:

- `src/types/domain.ts` の型に **必須の項目を足す・項目を消す・名前を変える**(ダミーデータや他の人のコードが型エラーになる)
- `src/features/*/index.ts` から外に出している部品の引数(props)の型(受け渡しの形=契約が変わる)
- `src/data/index.ts` で公開している関数やフックの引数・戻り値

### 4. 土台担当への連絡が必要な変更(新規追加でも該当)

次のどれかに当てはまったら、**PR を出す前に土台担当に連絡が必要** と伝える。

| 対象                                                        | 理由                                                                             |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `package.json` に **ネイティブ部品** を追加・削除・更新した | 配布済みの開発ビルドと食い違い、全員のアプリが起動しなくなる。ビルドし直しが必要 |
| `app.json` / `app.config.*` / `eas.json` を変えた           | アプリの設定(権限・名前など)はビルドし直しが必要                                 |
| `supabase/` の中(DB の変更、シード)を変えた                 | 全員が使っている DB に影響する                                                   |
| `src/lib/supabase.ts` を変えた                              | データの接続部分は土台担当が管理している                                         |
| `.env` などの秘密情報がコミット対象に入っている             | 鍵が外に漏れる                                                                   |

**ネイティブ部品かどうかの見分け方**:追加された部品について、`node_modules/<部品名>/` の中に `ios/` フォルダ、`*.podspec`、`expo-module.config.json` のどれかがあればネイティブ部品と判断する。迷ったらネイティブとして扱う。
ネイティブ部品なら、リポジトリ直下の `NATIVE_DEPS.md` に載っているか確認する。載っていなければ、今の開発ビルドでは動かない。
JavaScript だけの部品なら追加してよい。その場合も `npx expo install --check` でバージョンの組み合わせに問題がないか確認する。

### 5. /code-review を実行する

`code-review` スキルを `medium` で実行し、壊れそうな箇所(バグ)がないか確認する。
指摘があれば、直すかどうかをユーザーと相談する。

### 6. 結果をまとめる

次の形で報告する。

```
## pre-merge の結果:OK / 要対応 / 土台担当に連絡が必要
- 型・Lint:
- 担当フォルダ外の既存の変更・削除:
- 土台担当への連絡が必要な変更:
- code-review:
- 残っている作業:
```

最後に、**自分の iPhone でアプリが起動し、変更した画面が動くことを確認したか** を必ず聞く。まだなら、確認してから PR を出すように伝える。

### 7. PR の本文を書く

PR の本文は、このプロジェクトの **作業ログ** になります。土台担当は後からこれを読んで、何が変わったかを把握します。
会話の中で相談した内容(なぜその方法にしたか、既存を変えた理由)も含めて、次のテンプレートで書く。

```markdown
## 目的

<!-- 何のための変更か。1〜2文 -->

## 変更内容

### 新規追加

-

### 既存の変更・削除(担当フォルダ外のもの)

<!-- なければ「なし」 -->

- 対象:
  - 変えた理由(Claude と相談した内容):
  - 影響を受ける場所:

## 他のメンバーへの影響

<!-- なし / あり(誰が何をする必要があるか) -->

## ネイティブ部品・アプリ設定

<!-- 追加なし / あり(土台担当に依頼済みか) -->

## 確認したこと

- [ ] `npx tsc --noEmit` が通る
- [ ] `npx expo lint` が通る
- [ ] /code-review の指摘を確認した
- [ ] 自分の iPhone で起動し、変更した画面が動いた
```

- `gh` コマンドが使え、ユーザーが了承すれば `gh pr create` で PR を作る。使えなければ、本文をそのまま貼れる形で出す。
- 「他のメンバーへの影響」が「あり」なら、PR のリンクをチームのチャンネルでも共有するよう伝える。PR を見ていない人にも届くようにするため。
